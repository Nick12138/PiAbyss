## 语义梳理：委派任务 ≠ 消息（代码确认）
- 任务 = dispatch record（dispatchId，持久化 dispatches.json）。一次 pixie_dispatch 调用 = 一条 record；`<pixie-dispatch>` 信封注入只是启动手段，queued 任务在出队前**没有任何消息存在**。
- 回合归属（watchDispatchTurn envelopeSeen）：仅含信封的首 turn 触发自动回调，后续续聊轮不触发。
- 插话 interject：不建 record，骑原 dispatchId（仅 dispatched/awaiting_user 接受）；答复 reply：原 record 复活（awaiting_user→dispatched），`<pixie-reply>` 注入同会话；二者都**不算新任务**。
- 再次 dispatch 同一会话 = 新任务：有 LIVE 委派（dispatched/paused/awaiting_user）→ 登记 queued 且信封不发送（引擎持有 per-session 队列，前一个终态后 drainQueueAfterSettle 出队注入）；无 LIVE 但 busy → record 已建，信封走 SDK followUp 队列。
- 用户手动往被委派会话发消息：不建 record、不占队列门（"Manual user turns never hold the gate"），turn 无信封不触发回调。
- retry：resume 复用原 record（非新任务）；redispatch 新 record（retryOf 链，算新任务）。

## 修复：委派面板归属过滤失效（每个会话都显示同样 2 条历史）
- 用户报障：打开任何小精灵会话，面板都显示"已结束 2"。根因两个：① 旧记录（10-12）无 originSessionId 字段，加载归一为 null，而过滤规则把 null 当"全段可见"兜底 → 旧记录每个会话都出现；② 过滤 key 用 runner 指针（锚点），不是用户当前打开的会话，弹窗切会话列表不变。
- 修复（严格归属语义）：`listDispatchesForPanel` = 活跃（dispatched/queued/paused/awaiting_user，跨会话必须可见可操作）∪ originSessionId === 当前会话；null 归属不再兜底，拿不到会话上下文时只显示活跃。
- `pixie.dispatches` RPC 参数改 `{ sessionId?: string | null }`（validate/contracts/coverage 同步；null 兼容旧前端）；前端 refreshDispatches 传「当前打开的会话 id」，PixiePage 把 panelSessionId 加进轮询 effect 依赖 → 切会话立即重拉。
- 旧记录归属反推：loadDispatches 对缺 origin 的记录用 v4 timeline.json 段窗口按 createdAt 落段反推（timeline 只读保留）；推不出保持 null（不显示）。真实数据验证：2 条旧记录正确归到 01a12f34（10-12 那段）。
- 前端补 pending 重拉：in-flight 期间归属变化（切会话）落地后立即补拉，消除最长 5s 轮询延迟。
- 已知局限：归属注入仍用 runner 指针（currentPixieSessionId）。若用户在弹窗里打开旧会话并在那里跟小精灵聊天，新派发会被记到锚点段。彻底修复需 pi-pixie 插件在 dispatch body 里带上 sessionIdFromCtx（插件经 git source 加载，改动要 push 才生效，暂缓）。

## 调研：三个 pi 记忆插件对比（pi-memory / pi-hermes-memory / gentle-engram）
- 动机：给 PiAbyss 的记忆机制选型做参考（现存设计文档《小精灵记忆与晨间问候设计.md》）。
- **pi-memory**（jayzeng，v0.4.2）：纯 Markdown（MEMORY.md + daily + scratchpad），零依赖核心，qmd 可选三档搜索（BM25/向量/混合）；KV cache 稳定快照设计；可恢复删除。周下载 12.4k 最高、star 191 最低，更新放缓（9-21 push）。
- **pi-hermes-memory**（chandra447，v0.9.10）：移植自 Nous Hermes；Markdown + SQLite(FTS5) 双存；唯一支持全量历史会话搜索；6 类记忆分类 + 全局/项目双层；后台自动学习循环（每10轮一次 LLM 调用=持续成本）；密钥扫描。硬伤：better-sqlite3 原生模块（Windows ABI 风险）+ 中文 trigram 需≥3字符（1-2 字汉字搜不到）。更新最勤（10-11 push）。
- **gentle-engram**（Gentleman Programming，v0.4.2）：独立记忆系统（Go 单二进制 + SQLite/FTS5 + 本地 HTTP 7437 + MCP），唯一支持跨 agent 共享记忆（Claude Code/Cursor/Codex 等）；社区最热（7.2k star）但架构最重（需装 Go binary 起服务）、扩展/core 版本锁定矩阵复杂。数据存 `~/.engram` 非 git 友好。
- 结论倾向：纯 pi 场景最小侵入选 pi-memory；要自动学习+会话检索选 hermes（中文/Windows 短板需验）；要多 agent（WorkBuddy/pi/CC）共享一份记忆只有 engram。
- 需求澄清（Nick）：记忆**只给小精灵**（pixie 工作区专用），其他工作区一概不要；期望小精灵"记住很多事情"。推荐 pi-hermes-memory（自动学习循环=不靠用户主动喊记；双层记忆按 cwd 天然项目隔离；容量自动整合；llmModelOverride 可指便宜模型摊薄审查成本），备选 pi-memory（`PI_MEMORY_DIR` 指向 pixie 专属目录=最干净隔离，但无自动学习需 pixie 系统提示写记忆守则），engram 排除（Go 服务太重且天然记录其他工作区）。落地前提：宿主按 pixie 会话挂扩展才能严格隔离；Windows better-sqlite3 编译待验。
