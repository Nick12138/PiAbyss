# Bug 分析过程

> ⚠️ **勘误（2026-09-15）**：本文档第 2、3 节关于“只有 display:true 的 custom_message
> 才会进入 session.messages”的论断与 pi 核心代码事实**相反**——运行时与恢复路径都会
> 让每条 custom_message 占据 session.messages 一个位置。因此原 bug 的真正根因是
> 悬挂 message 条目被错误计数（已由 `5d60777` 修复），而据此推出的 `d305598` 修复
> 引入了尾部重复渲染的回归（已由 `b9c8711` 修复）。详见
> [4-勘误与回归修复.md](./4-勘误与回归修复.md)。以下为原文存档。

## 问题定位

### 关键文件
- `apps/desktop/src/features/chat/transcript-model.ts`
- 核心函数：`sourceMessages()`

### 根本原因

在 `transcript-model.ts` 的 `sourceMessages()` 函数中，存在**长度对齐计算错误**。

#### 错误逻辑分析

```typescript
// 原始错误代码（简化）
if (type === "custom_message") {
  projectedMessageCount += 1;  // ❌ 无条件计数
  const message = entryProjectedMessage(record, () => ({
    role: "custom",
    customType: typeof record.customType === "string" ? record.customType : "custom",
    content: (record.content as SerializableAgentContent[] | string) ?? "",
    display: record.display === true,  // 这里判断了 display
    // ...
  })) as SerializableAgentMessage;
  sources.push({ kind: "message", message, ... });
}
```

#### 问题所在

1. **`projectedMessageCount` 的作用**
   - 用于统计 `entries` 中有多少条目应该投影为 `messages`
   - 用于后续的长度对齐计算：`const tailStart = Math.min(projectedMessageCount, messages.length);`

2. **错误的计数逻辑**
   - 代码对**所有** `custom_message` 类型的条目都执行 `projectedMessageCount += 1`
   - 但实际上，只有 `display: true` 的 custom_message 才会进入 `session.messages` 数组
   - `display: false` 的 custom_message 仍然是一个 entry，但**不会**出现在 messages 中

3. **导致的后果**
   ```typescript
   // 当存在 display:false 的 custom_message 时
   projectedMessageCount = 10  // 虚高：包含了不应该计数的条目
   messages.length = 9         // 实际：只有 9 条消息
   
   tailStart = Math.min(10, 9) = 9
   
   // 后续处理实时消息
   for (let index = tailStart; index < messages.length; index++) {
     // 因为 tailStart = 9，而 messages.length = 9
     // 循环条件 9 < 9 为 false，循环不执行
     // 实时尾部消息（包括刚发送的用户气泡）被跳过！
   }
   ```

4. **实际影响**
   - 刚发送的用户消息气泡属于"实时尾部消息"
   - 由于 `tailStart` 偏大，这些消息被排除在渲染之外
   - 用户消息气泡消失

## 白色方块的来源

### 为什么会出现流式光标？

1. **`findStreamingAssistantKey()` 函数的作用**
   - 用于找到当前正在流式输出的 assistant 消息
   - 如果找到，会在该消息下方显示流式光标（▋）

2. **误判逻辑**
   ```typescript
   function findStreamingAssistantKey(
     rows: readonly TranscriptRow[],
     messages: readonly SerializableAgentMessage[],
     isStreaming: boolean,
   ): string | undefined {
     if (!isStreaming) return undefined;
     const tailRow = rows[rows.length - 1];
     if (tailRow?.role !== "assistant") return undefined;
     
     const lastMessage = messages[messages.length - 1];
     if (!lastMessage || lastMessage.role !== "assistant" || 
         numberField(lastMessage, "endedAt") !== undefined) {
       return undefined;
     }
     
     return tailRow.key;  // ❌ 误判：上一条已结束的消息被当作流式中
   }
   ```

3. **为什么会误判？**
   - 当用户气泡被"吞掉"后，`rows` 数组的最后一项变成了上一条 assistant 消息
   - 虽然这条消息实际上已经结束（有 `endedAt`），但由于某些边界情况
   - 该函数仍然将其判定为"流式中"
   - 于是白色方块（流式光标）出现在已结束的消息下方

### 光标字符

- Unicode: U+258B (LEFT FIVE EIGHTHS BLOCK) ▋
- 在 Streamdown 组件中用作流式输出的视觉提示
- 正常情况下只应出现在**正在流式输出**的消息中

## 为什么切换会话能恢复？

### 切换会话的处理流程

1. 切换会话时触发 `applySessionSnapshot`
2. 走完整的快照重算流程
3. 重新计算所有行模型（`buildTranscriptRows`）
4. 此时会从头开始构建，绕过了之前的长度对齐错误

### 为什么能绕过错误？

- 快照重算时，会重新遍历所有 entries
- 重新构建 messages 数组
- 虽然计数逻辑仍然错误，但在完整重算中，某些边界条件被重置
- 或者实时消息队列被清空重建，临时规避了问题
- 但**根本问题没有解决**，下次发送消息可能再次触发

## 为什么只影响部分会话？

### 触发条件

只有当会话中存在以下情况时，才会触发这个 bug：

1. **存在 `display: false` 的 `custom_message` 条目**
   - 这类条目是一个 entry，但不进入 messages
   - 导致 `projectedMessageCount` 虚高

2. **常见来源**
   - 系统内部消息（如状态更新、元数据记录）
   - 扩展插件产生的内部消息
   - 某些特殊的自定义消息类型

### 不受影响的会话

- 只包含标准的 user/assistant 消息
- 没有 custom_message，或所有 custom_message 都是 `display: true`
- 这些会话的 `projectedMessageCount` 计数是准确的，不会触发 bug

## 时间线

1. 会话中积累了一些 `display: false` 的 custom_message
2. `projectedMessageCount` 开始虚高
3. 用户发送新消息
4. 新消息被加入 messages 数组（乐观回显）
5. `sourceMessages()` 计算 `tailStart` 时，由于计数虚高，导致 tailStart 过大
6. 实时尾部消息（包括新发送的用户气泡）被跳过
7. 用户气泡消失，上一条 assistant 消息被误判为流式中
8. 白色方块出现
9. 用户切换会话，触发快照重算
10. 临时恢复正常（但下次可能再发）
